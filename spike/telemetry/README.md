## 0. Перевірити воркер локально (нічого встановлювати не треба)

```bash
node spike/telemetry/worker/test.mjs
```

25 перевірок: відмова пакету з координатами (дзеркало клієнтського гарда D14), форма ключа в R2, від
якої залежить скрипт аналізу, і — окремим блоком — що читання **закрите**: без адмін-секрета, чужим
секретом, клієнтським секретом і при секреті, що дорівнює клієнтському.

## 1. Деплой воркера (частина Дениса — акаунт твій)

Один раз:

```bash
npm install -g wrangler
```

```bash
cd spike/telemetry/worker && wrangler login
```

Секрет **клієнта** (це не автентифікація, а фільтр від випадкового трафіку — він однаково лежатиме в
APK; вигадай будь-який довгий рядок):

```bash
cd spike/telemetry/worker && wrangler secret put TELEMETRY_KEY
```

Секрет **на читання** — другий, ІНШИЙ рядок:

```bash
cd spike/telemetry/worker && wrangler secret put TELEMETRY_ADMIN_KEY
```

⚠️ Саме інший, не той самий. Клієнтський лежить у APK і витягується розпакуванням застосунку; якби
ним відкривалось і читання, будь-хто, хто розпакував APK, прочитав би телеметрію всіх тестерів.
Воркер відмовляє при збігу цих двох значень, тож «зекономити на одному секреті» не вийде — читання
просто не працюватиме.

Деплой:

```bash
cd spike/telemetry/worker && wrangler deploy
```

Wrangler надрукує адресу виду `https://streif-telemetry.<твій-акаунт>.workers.dev`.

**Перевірити, що живе** (має відповісти `nope` — тобто воркер працює й секрет перевіряється):

```bash
curl -X POST -d '{"install":"test"}' https://streif-telemetry.ВСТАВ-СВОЄ.workers.dev
```

## 2. Увімкнути надсилання в застосунку

Два рядки в `app/build.gradle.kts`:

- `TELEMETRY_URL` — адреса з кроку 1;
- заголовок `x-streif-key` — той самий секрет.

⚠️ Доти `TELEMETRY_URL` порожній, і застосунок **у мережу не ходить узагалі** — накопичує лічильники
й мовчить. Це нормальний стан, а не «зламано».

⚠️ Секрет у `build.gradle.kts` = секрет у git. Для закритого тесту це прийнятно (він захищає bucket від
випадкового сміття, а не дані від людей), але **в продакшн так не переносити** — там телеметрії
взагалі не буде. *(Станом на 2026-07-29 обидва значення винесені в gitignored `telemetry.properties`
поруч із `keystore.properties`, тож у git їх уже немає.)*

## 3. Зняти дані

Один раз на сесію (PowerShell):

```powershell
$env:STREIF_TELEMETRY_URL = "https://streif-telemetry.ВСТАВ-СВОЄ.workers.dev"
```

```powershell
$env:STREIF_TELEMETRY_ADMIN_KEY = "той-самий-рядок-що-в-TELEMETRY_ADMIN_KEY"
```

```bash
python spike/telemetry/fetch_telemetry.py ./dump
```

Можна звузити період: `--since=2026-08-01`. Скрипт **без залежностей** (лише stdlib) і пропускає те,
що вже лежить у теці, тож повторний запуск дешевий.

⚠️ **Читає через воркер, а не з R2 напряму — і це свідомо.** Перша версія ходила в R2 через `boto3` з
`R2_ACCOUNT_ID`/`R2_ACCESS_KEY`/`R2_SECRET_KEY`. Дві причини відмовитись: сторонній пакет, якого на
машині не було (перший же запуск упав на `ModuleNotFoundError`), і — головніше — ті креденшели дають
доступ до **всіх** bucket-ів проєкту, включно з продакшн-тайлами. Заради читання кількох десятків
JSON-ів на диску лежав ключ від усього. Адмін-секрет воркера відкриває рівно телеметрію.

⚠️ **`wrangler r2 object get … --prefix … --local-directory …` не існує.** Перевірено на живому
wrangler 4.115 (2026-07-29): `r2 object get` бере РІВНО ОДИН об'єкт у формі `<bucket>/<key>`, ні
`--prefix`, ні `--local-directory` немає. Тобто спосіб, який README радив спершу, впав би рівно тоді,
коли дані вперше знадобляться.

⚠️ Bucket **`streif-telemetry`**, не `streif-tiles`: у того ввімкнено публічний Development URL, а
публічний доступ в R2 діє на весь bucket одразу — телеметрія лежала б відкрито. Причина докладно —
в коментарі у `worker/wrangler.toml`.

Якщо треба глянути очима, без скрипта:

```bash
curl -H "x-streif-admin: СЕКРЕТ" https://streif-telemetry.ВСТАВ-СВОЄ.workers.dev/list
```

`405 streif telemetry` у відповідь означає «секрет не той або не заведений» — воркер свідомо не
відрізняє це від «такого шляху немає», щоб відповідь не підтверджувала, що за `/list` щось стоїть.

## 4. Подивитись

python spike/telemetry/analyze_telemetry.py ./dump

Скрипт відповідає на ті самі чотири питання, заради яких телеметрію вмикали: якість матчингу поза

`spike/fieldtest/analyze.py`.

## Що приймач НЕ пише — і чому це важливо

- **IP-адреси.** `cf-connecting-ip` є в кожному запиті й це персональні дані за GDPR. Записати його
  означало б перетворити «знеособлену статистику» на прив'язану до людини, тобто збрехати в тексті
  згоди. Воркер його не читає, Logpush для нього не вмикати.
- **Нічого схожого на координати.** Воркер відхиляє такий пакет із `422` — це дзеркало клієнтського
  гарда (`TelemetryTest.noModelFieldCanCarryACoordinate`) з іншого кінця дроту. Клієнт може
  відкотитись, стара збірка може лишитись у когось на телефоні; дешевше відмовити тут, ніж потім
  чистити bucket.
- **Нічого не віддає без адмін-секрета.** Читання (`/list`, `/get`) закрите окремим секретом, і — на
  відміну від запису — **fail closed**: немає секрета в оточенні воркера, немає доступу. На записі
  перевірка навпаки пропускає все при порожньому секреті, і на цьому 2026-07-29 приймач кілька хвилин
  постояв відкритим; для читання така поведінка коштувала б не сміття, а даних тестерів.

## Коли тест скінчиться

1. `wrangler delete` для воркера;
2. `wrangler r2 bucket delete streif-telemetry` — bucket цілком (він лише під тест, тож вичищати
   окремі префікси не треба);
3. прибрати телеметрію із застосунку (4 кроки в `app/build.gradle.kts`);
4. видалити цю теку.
