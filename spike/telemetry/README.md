# Телеметрія закритого тесту (D39) — приймач і аналіз

> ⚠️ **Усе в цій теці тимчасове.** Живе рівно стільки, скільки закритий тест, і прибирається разом
> із текою `telemetry/` у застосунку (інструкція — в `app/build.gradle.kts` біля прапорця).
> Канон рішення — `docs/DECISIONS.md` **D39**; стан пунктів — `docs/release-checklist.md` §B.6.5.

Що збирається й навіщо — у D39. Тут лише «як підняти й як подивитись».

---

## 0. Перевірити воркер локально (нічого встановлювати не треба)

```bash
node spike/telemetry/worker/test.mjs
```

10 перевірок, зокрема відмова пакету з координатами (дзеркало клієнтського гарда D14) і форма ключа
в R2, від якої залежить скрипт аналізу.

## 1. Деплой воркера (частина Дениса — акаунт твій)

Один раз:

```bash
npm install -g wrangler
```

```bash
cd spike/telemetry/worker && wrangler login
```

Секрет (це не автентифікація, а фільтр від випадкового трафіку — він однаково лежатиме в APK;
вигадай будь-який довгий рядок):

```bash
cd spike/telemetry/worker && wrangler secret put TELEMETRY_KEY
```

Деплой:

```bash
cd spike/telemetry/worker && wrangler deploy
```

Wrangler надрукує адресу виду `https://streif-telemetry.<твій-акаунт>.workers.dev`.

**Перевірити, що живе** (має відповісти `nope` — тобто воркер працює й секрет перевіряється):

```bash
curl -X POST -d '{"install":"test"}' https://streif-telemetry.ВСТАВ-СВОЄ.workers.dev
```

## 2. Увімкнути надсилання в застосунку

Два рядки в `app/build.gradle.kts`:

- `TELEMETRY_URL` — адреса з кроку 1;
- заголовок `x-streif-key` — той самий секрет.

⚠️ Доти `TELEMETRY_URL` порожній, і застосунок **у мережу не ходить узагалі** — накопичує лічильники
й мовчить. Це нормальний стан, а не «зламано».

⚠️ Секрет у `build.gradle.kts` = секрет у git. Для закритого тесту це прийнятно (він захищає відро від
випадкового сміття, а не дані від людей), але **в продакшн так не переносити** — там телеметрії
взагалі не буде.

## 3. Зняти дані з R2

```bash
wrangler r2 object get streif-tiles --prefix telemetry/ --local-directory ./dump
```

Якщо версія wrangler не вміє `--prefix` для `get` — простіше через `rclone` з S3-сумісним доступом до
R2, або скачати теку з панелі Cloudflare. Об'єкти лежать як `telemetry/<день>/<install>-<ts>.json`,
тож можна брати за період.

## 4. Подивитись

```bash
python spike/telemetry/analyze_telemetry.py ./dump
```

Скрипт відповідає на ті самі чотири питання, заради яких телеметрію вмикали: якість матчингу поза
Volda · виживання прогулянки на чужих OEM · здоров'я даних · retention (P10). Без залежностей, як і
`spike/fieldtest/analyze.py`.

## Що приймач НЕ пише — і чому це важливо

- **IP-адреси.** `cf-connecting-ip` є в кожному запиті й це персональні дані за GDPR. Записати його
  означало б перетворити «знеособлену статистику» на прив'язану до людини, тобто збрехати в тексті
  згоди. Воркер його не читає, Logpush для нього не вмикати.
- **Нічого схожого на координати.** Воркер відхиляє такий пакет із `422` — це дзеркало клієнтського
  гарда (`TelemetryTest.noModelFieldCanCarryACoordinate`) з іншого кінця дроту. Клієнт може
  відкотитись, стара збірка може лишитись у когось на телефоні; дешевше відмовити тут, ніж потім
  чистити відро.

## Коли тест скінчиться

1. `wrangler delete` для воркера;
2. видалити префікс `telemetry/` у відрі;
3. прибрати телеметрію із застосунку (4 кроки в `app/build.gradle.kts`);
4. видалити цю теку.
